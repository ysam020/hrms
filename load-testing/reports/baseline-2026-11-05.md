# Praesto baseline: 2026-11-05

**What this is:** the first baseline from the Autocannon framework in `load-testing/`, before any optimisation. Code under test: branch `feature/perf-caching-observability` at 64a67b8, plus two default-off switches the test stack needs (rate-limit env overrides, a CloudWatch log off-switch). All timestamps below are UTC.

**Kind of result:** comparative. The application ran in the isolated `hrms-loadtest` Docker stack, with per-container limits equal to production's, on the same MacBook as the load generator. The database was the shared Atlas cluster that also serves production. This is not a measurement of production capacity (see Limitations).

At about 45 req/s the system is bound by database round trips, not by Praesto's own CPU, memory or event loop. Concurrency beyond about 10 adds queueing, not throughput. Pushing harder also drives the stack's Prisma pools toward the cluster's 500-connection limit, which production shares.

## Findings (prioritised; nothing was changed to address them)

**Critical**

1. **The shared Atlas tier is the capacity ceiling, for production too.** It degrades about 10× at roughly 100–130 ops/s cluster-wide, so a few dozen concurrent users of any tenant slow everyone. Until the tier changes, no application optimisation can lift throughput much above ~45 req/s from this stack. It can only cut queries per request.
2. **The services' Prisma pools can exhaust the cluster's 500-connection limit.** The idle test stack held ~110 connections, and 100 concurrent connections pushed the cluster to 407 within 23 s. Production runs the same 12 services × 2 workers with the same pools (`maxPoolSize=50` per tenant client, plus master clients), and the local dev stack holds more. A real traffic spike can starve production of connections. This confirms open backlog item 7 (architecture audit §4).

**High** 3. **Gateway memory is at 90–93% of its prod limit at rest** (690–710 MiB of 768 MiB for primary + 2 workers). Under load, or with one more cached tenant client, the OOM killer is next. Measured on both the dev and loadtest stacks. 4. **Round trips per request dominate latency.** `/dashboard/data` runs a median of 10 queries (up to 8 in flight) and spends 2.6 s of database time per request. The `db-heavy` routes above are the first targets for the per-change optimisation plan: permission caching, redundant permission queries, dashboard consolidation. 5. **`/analytics/headcount`, `/analytics/attendance` and `/analytics/leave` return HTTP 500** (`client[method] is not a function`) for every role. This is a functional bug, so they are excluded from the workload.

**Medium** 6. `GET /get-all-users?limit=1000` returns **201 KB** per call (capped at 200 users). It's used by pickers and the directory. 7. Master `User.findUnique` is the most frequent slow query (68 in 30 s). It's the per-handler permission and superuser lookup from the Phase 1 audit, and the target of the permission-context cache.

## Limitations

- The generator and the application share one machine. Containers carry prod's per-container limits, but unlike prod's 2-vCPU host they don't compete for two cores. Absolute numbers are an optimistic comparative baseline.
- Atlas CPU, memory, disk, profiler, `$queryStats`, pool wait time and per-query execution stats can't be read on this tier. Only `serverStatus` connections, op counters, network bytes and round trip are reported. Cluster figures include production traffic.
- Every query crosses the internet from the Mac to Atlas (~40 ms idle round trip). Prod runs in ap-south-1, nearer the cluster, so its per-query time is lower. The tier's degradation under load applies to both.
- Requests run with no think time (closed loop). One connection is far more demanding than one person.
- The 10-connection figures come from a 30-second window (Prometheus scrapes every 15 s), so server-side numbers are coarse.
- Cleanup has not been run yet. The synthetic data stays in place for the before/after runs and keeps the cluster at **494 of 500 collections**.
