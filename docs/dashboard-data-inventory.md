# Dashboard data inventory

What Praesto actually stores and serves that a dashboard can use, traced from
the Prisma models (`packages/database/src/prisma/schema.prisma`) through the
gateway handlers (`apps/api-gateway/src/handlers`) to the web app. Written
before the dashboard redesign (October 2026) and updated when it shipped.

## How access is decided today

Praesto has **no single role model**. Access is the union of three things,
and every handler combines them its own way:

| Mechanism         | Where it lives                                                                            | Values                                                                                                        |
| ----------------- | ----------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| Tenant role       | `TenantMembership.role`, copied into the JWT as `tenantRole`                              | `owner`, `admin`, `hr`, `manager`, `employee`                                                                 |
| Superuser flag    | `User.isSuperUser` (master DB)                                                            | Owners are backfilled to `true`                                                                               |
| Permission grants | `User.permissions: string[]`, copied from custom `Role` documents when a role is assigned | `Module:action[:scope]`, scope `self` / `team` / `all`; catalog in `packages/common/src/permissionCatalog.ts` |
| Team leadership   | `Team.teamLeaderId` + `Team.members[]`                                                    | Used as the reporting manager by approval chains, WFH notifications and performance reviews                   |

Facts that shape the dashboard:

- **No default permission sets exist.** An ordinary employee has an empty
  `permissions` array; self-service (punching in, applying for leave, viewing
  your own records) is implicit, not granted.
- **"HR or above"** (`owner`/`admin`/`hr`, or a superuser) is the gate on
  every organisation-wide list: attendance, leave, payroll runs, asset and
  helpdesk statistics, analytics (`authorize("owner","admin","hr")`).
- **The `team` scope is not enforced anywhere.** `Attendance:view:team` and
  `Leave:view:team` exist in the catalog and the permissions editor, but
  `/get-all-attendances` and `/get-leave-applications` only ever return "all"
  (HR or above) or "self". The only working notion of a team is
  `Team.teamLeaderId`. The dashboard therefore scopes team data to **members of
  teams the user leads** — the same rule approvals already use — and adds no
  wider access.
- **`manager` is not used by any authorization check.** It is accepted as a
  membership role but no handler admits it; leadership comes from `Team`.
- **Tenant isolation** is structural: every business model lives in a
  per-tenant database (`prismaWithTenant`), and `User` queries in the shared
  master DB get `tenantId` injected automatically.

### Authorization gaps found during the audit

| Endpoint                             | Problem                                                                                                                                                                                 | Status                                                                                                              |
| ------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| `GET /employee-insights`             | No role check — any signed-in employee received organisation-wide headcount and the department breakdown. The old dashboard requested it for everyone and only hid the panel in the UI. | **Fixed:** now `requireHrPrivileged`.                                                                               |
| `GET /get-kyc-insights`              | No role check — anyone received organisation-wide KYC counts.                                                                                                                           | **Fixed:** HR or above, or `BasicKYCDetails:view_kyc:all` / `approve_kyc:all`.                                      |
| `employee-insights` "totalEmployees" | `user.count()` with no status filter: terminated, resigned and absconded people count as headcount.                                                                                     | The new dashboard reports **active** headcount and labels it so. The endpoint is unchanged for the Insights screen. |

## Data points

Refresh: **live** = refetched every 2 minutes while the page is visible and on
focus; **slow** = every 15 minutes and on focus; **on change** = after a
mutation on the dashboard (punch, decision) plus focus.

| Asked for                       | Why not                                                                                                                                                                                               |
| ------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Late arrivals, early departures | _Corrected:_ late arrivals are recorded (status "Late", tenant-wide start time plus grace period) but evaluated without a tenant time zone; early departures aren't recorded. See dashboard-audit.md. |

| Expiring documents              | KYC documents have no expiry date.                                                                                                                                                                    |

## What shipped

**Endpoints** (`apps/api-gateway/src/handlers/dashboard.ts`, mounted behind `subscriptionGuard`):

| Endpoint                        | Purpose                                                                                                                                                                                                       |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /dashboard`                | The caller's capabilities, personas, the widgets they may use (with sizes and setting options), the role default and their layout                                                                             |
| `GET /dashboard/data?ids=…`     | Data for the listed widgets. Each comes back `{ ok, data }`, or `{ ok: false, error: "forbidden" \| "failed" }` — one failing widget never fails the rest. Settings come from the saved layout, not the query |
| `PUT /dashboard/preferences`    | Save `{ version: 1, widgets: [{ id, visible, size, settings }] }`; stored sanitized                                                                                                                           |
| `DELETE /dashboard/preferences` | Back to the role default                                                                                                                                                                                      |

**Registry.** The server registry (`apps/api-gateway/src/config/dashboardWidgets.ts`) owns widget ids, required capabilities, sizes, settings and persona defaults. The web registry (`apps/web/src/features/dashboard/registry.tsx`) owns names, descriptions, icons, skeletons and renderers. A test keeps the two id lists identical.

**Preferences.** `DashboardPreference` in the tenant database, unique on `(tenantId, userId)`, so a person in two organisations has two layouts. Every read and write goes through `sanitizeLayout`: unknown or unauthorized widgets are dropped, sizes and settings validated (a team setting must be a team the caller leads, a department must exist), and newly available widgets are appended hidden. A stale or hand-edited row can hide or reorder, never grant. Deploy note: create the unique index in existing tenant databases (`pnpm --filter @hrms/db db:migrate`).

**Refresh.** Team Today and Organisation Today every 2 minutes; everything else every 15. Both groups also refresh on focus (at most once a minute) and pause while the tab is hidden. Each group is one request. Personal widgets reload after a punch.

**Offline.** The last good config and widget data are cached in the offline store under the signed-in scope, so a reload without a connection shows the dashboard with an offline banner and "Saved" times on server widgets; sign-out deletes the cache. Layout changes made offline wait in Pending Changes (`dashboard.layout`) and sync like any other edit.

**Tests.** `api-gateway/src/__tests__/dashboardWidgets.test.ts` (defaults per persona, multi-role merge, sanitizing), `dashboardHandlers.test.ts` (capabilities from real permission data, forbidden widgets, team scoping, saved settings only, partial failure, tenant-scoped preferences, reset), `employeeHandlers.test.ts` (KYC insights now restricted), and `apps/web/src/__tests__/dashboard.test.tsx` (registry parity, Customize only offers listed widgets, hide/show/reorder).

## Known limitations

- Team scope is "teams you lead". Nested reporting (a lead's lead) isn't modelled anywhere in Praesto, so a department head sees only teams they lead directly.
- Organisation Today doesn't separate late arrivals yet; the "Late" status exists but its time-zone handling needs confirming first (dashboard-audit.md).
- Attendance Trend divides by today's active headcount and counts people on leave as not in.
- Headcount Trend can't place former employees without an exit date; it says how many it left out.
- Widget sizes are Standard and Wide on a two-column grid; there is no free-form resizing.
