# Field encryption

Personal data is encrypted in the application before it reaches MongoDB. Someone who can read the database, a dump or a backup sees ciphertext, plus keys they can't unwrap without AWS KMS.

## How it works

| Part           | Where                                          | What it does                                                                                                               |
| -------------- | ---------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| Field registry | `packages/database/src/piiRegistry.ts`         | Lists every protected field (202, in 41 models) with its type and lookup rule. A field not listed here is not protected.   |
| Cipher         | `packages/crypto/src/fieldCipher.ts`           | AES-256-GCM, a fresh random 96-bit IV per value. Scope, key version, model and field are bound as authenticated data.      |
| Keys           | `packages/database/src/fieldKeys.ts`           | One data key per scope and purpose. Wrapped by KMS, stored in `encryption_keys`, cached unwrapped in memory for 5 minutes. |
| Prisma hook    | `packages/database/src/fieldProtection.ts`     | Attached to the master client and every tenant client. Seals writes, opens reads, rewrites lookups.                        |
| Validators     | `packages/database/src/fieldValidators.ts`     | MongoDB `$jsonSchema` on each protected collection: plaintext in a protected field is rejected, whatever wrote it.         |
| Migration      | `packages/database/src/migrate-encrypt-pii.ts` | Seals existing rows, in batches, resumable.                                                                                |

### Stored format

```
enc:v2:<scope>:<keyVersion>:<iv>:<tag>:<ciphertext>
```

`scope` is `master` or the tenant's database name. Numbers, dates, booleans and JSON keep their type through a one-letter tag inside the encrypted body. Null, absent and empty-string values are stored as they are.

Fields that were `Float`, `DateTime` or `Boolean` are `Json` in the schema, because the stored value is a string. Read them with `protectedNumber` / `protectedDate` from `@hrms/db/values`; at runtime the hook already returns the original type.

### Keys

| Scope      | Database                                | Purposes      |
| ---------- | --------------------------------------- | ------------- |
| `master`   | master (`users`, `tenants`, `leads`, …) | `enc`, `bidx` |
| `<dbName>` | each tenant database                    | `enc`, `bidx` |

- `enc` keys encrypt values. `bidx` keys compute keyed hashes for exact-match lookups. The two never share a key.
- Each data key is generated by KMS `GenerateDataKey` with encryption context `{app: "praesto-field-encryption", scope, purpose}`, so a wrapped key only unwraps for its own scope.
- A value sealed for one scope does not open in another, even with the right key.
- Keys are created on first use. A process that isn't allowed to write sensitive data (development on a shared database) never creates them.

### Lookups and search

- **Exact match** on `User.username`, `User.email` and other email fields, and `Candidate.mobile`, uses a sibling `<field>_bidx` keyed hash. Email and mobile are normalised first. `findUnique`, `update` and `delete` by these fields work as before.
- **Uniqueness** of username and email is enforced by unique partial indexes on `username_bidx` and `email_bidx`. The old indexes now cover ciphertext and enforce nothing.
- **Substring search, ranges and sorting** on an encrypted field run in memory, on the rows the database can narrow to (one tenant, other filters applied). Above `FIELD_MEMORY_SCAN_LIMIT` rows (default 10,000) the query fails rather than return a partial answer.
- **Refused:** `groupBy`/`aggregate` over an encrypted field, relation filters on one, `increment` on an encrypted number, and raw pipelines that match, sort or group on one. Each throws `FieldProtectionError` so it is found in testing, not by a wrong number.
- **`aggregateRaw`** results have top-level protected fields opened. A `$lookup` result is not opened; use `openRawForCurrentDb(model, rows)`.

### Outside MongoDB

- Redis cache entries and queued notification and email jobs are sealed with a key derived from `CRYPTO_ENCRYPTION_KEY` (`sealTransient`).
- Log lines redact personal fields and scrub emails, phone numbers and ID numbers from text (`packages/logger/src/redaction.ts`).

## Configuration

| Variable                       | Where              | Meaning                                                                                          |
| ------------------------------ | ------------------ | ------------------------------------------------------------------------------------------------ |
| `FIELD_KMS_KEY_ID`             | production         | KMS key ARN or alias that wraps the data keys. Required in production.                           |
| `FIELD_KMS_REGION`             | optional           | Defaults to `AWS_REGION`, then `ap-south-1`.                                                     |
| `FIELD_KEK_HEX`                | development, tests | 64 hex characters. Used only when `FIELD_KMS_KEY_ID` is unset and `NODE_ENV` isn't `production`. |
| `FIELD_DEK_CACHE_TTL_MS`       | optional           | How long unwrapped keys stay in memory. Default 300000.                                          |
| `FIELD_KMS_TIMEOUT_MS`         | optional           | Per-attempt KMS request timeout. Default 3000; connect timeout 1 s; 3 attempts.                  |
| `FIELD_VALIDATION_LEVEL`       | optional           | `moderate` (default), `strict`, or `off`.                                                        |
| `FIELD_LEGACY_PLAINTEXT_MATCH` | optional           | Lookups also match rows not yet migrated. Set `false` once the migration is verified.            |
| `FIELD_MEMORY_SCAN_LIMIT`      | optional           | Row cap for in-memory search. Default 10000.                                                     |
| `CRYPTO_ENCRYPTION_KEY`        | all                | Still required: transient sealing, and reading values sealed by the earlier `enc:v1` scheme.     |

## AWS KMS

One symmetric key in the production account and region:

- Key policy: the account may administer the key but not use it for data. Only the application role may call `kms:GenerateDataKey` and `kms:Decrypt`, and only with all of these conditions:
  - `kms:EncryptionContext:app` equals `praesto-field-encryption`;
  - `kms:EncryptionContextKeys` is a subset of `app`, `scope`, `purpose`;
  - `scope` and `purpose` are present.
- The application needs no other KMS permission, not even `DescribeKey`.
- Deny `kms:ScheduleKeyDeletion` and `kms:DisableKey` when `aws:MultiFactorAuthPresent` is false. Removing that guard then needs a deliberate key-policy change.
- Enable automatic key rotation. KMS keeps old key material, so wrapped data keys stay readable.
- Deleting the key, or removing the role's access, makes every protected value unreadable. Use the 30-day deletion window, and alarm on `ScheduleKeyDeletion`, `DisableKey` and `PutKeyPolicy`.

Example key policy (replace the placeholders):

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "KeyAdministrationOnlyNoDataUse",
      "Effect": "Allow",
      "Principal": { "AWS": "arn:aws:iam::<account>:root" },
      "Action": [
        "kms:Describe*",
        "kms:Get*",
        "kms:List*",
        "kms:PutKeyPolicy",
        "kms:UpdateKeyDescription",
        "kms:CreateAlias",
        "kms:UpdateAlias",
        "kms:DeleteAlias",
        "kms:EnableKey",
        "kms:DisableKey",
        "kms:EnableKeyRotation",
        "kms:DisableKeyRotation",
        "kms:RotateKeyOnDemand",
        "kms:TagResource",
        "kms:UntagResource",
        "kms:ScheduleKeyDeletion",
        "kms:CancelKeyDeletion",
        "kms:RevokeGrant",
        "kms:RetireGrant"
      ],
      "Resource": "*"
    },
    {
      "Sid": "FieldEnvelopeUseByApplicationOnly",
      "Effect": "Allow",
      "Principal": { "AWS": "<application role arn>" },
      "Action": ["kms:GenerateDataKey", "kms:Decrypt"],
      "Resource": "*",
      "Condition": {
        "StringEquals": {
          "kms:EncryptionContext:app": "praesto-field-encryption"
        },
        "ForAllValues:StringEquals": {
          "kms:EncryptionContextKeys": ["app", "scope", "purpose"]
        },
        "Null": {
          "kms:EncryptionContext:scope": "false",
          "kms:EncryptionContext:purpose": "false"
        }
      }
    },
    {
      "Sid": "DenyDisableOrDeleteWithoutMFA",
      "Effect": "Deny",
      "Principal": { "AWS": "*" },
      "Action": ["kms:ScheduleKeyDeletion", "kms:DisableKey"],
      "Resource": "*",
      "Condition": { "BoolIfExists": { "aws:MultiFactorAuthPresent": "false" } }
    }
  ]
}
```

The role's own IAM policy grants the same two actions with the same conditions, on the key ARN only.

### Testing against real KMS

`integration/fieldKmsReal.it.test.ts` is skipped unless `FIELD_KMS_REAL_KEY_ID` is set. Use a dedicated test key and an identity that can use only that key, never the production key:

```
FIELD_KMS_REAL_KEY_ID=<test key arn> AWS_ACCESS_KEY_ID=… AWS_SECRET_ACCESS_KEY=… \
KMS_RESULTS_FILE=/tmp/kms.json NODE_OPTIONS=--experimental-vm-modules \
  npx jest -c integration/jest.integration.config.cjs integration/fieldKmsReal.it.test.ts
```

It checks the following, using synthetic data in the local containers:

- a round trip, with timings;
- a wrapped key opens only under its own scope and purpose;
- the identity is refused outside its policy;
- the application path creates a tenant's keys through KMS;
- behaviour when KMS is unreachable or a key is unknown.

While KMS is unreachable, already-unwrapped keys keep working until their cache entry expires. After that, the scope fails closed with `FieldKeyUnavailableError`.

## Operations

### Rotating a data key

`fieldKeyStore().rotate(scope, "enc")` adds a version; new writes use it and older versions still open. Then reseal existing values:

```
CONFIRM_DB_WRITE_HOST=<host> EXPECTED_KEK_ID=<kms key> \
  node packages/database/dist/migrate-encrypt-pii.cli.js --apply --rekey --database=all
```

### Migrating existing data

```
node packages/database/dist/migrate-encrypt-pii.cli.js --dry-run --database=all
node packages/database/dist/migrate-encrypt-pii.cli.js --verify --database=all
CONFIRM_DB_WRITE_HOST=<host> EXPECTED_KEK_ID=<kms key> \
  node packages/database/dist/migrate-encrypt-pii.cli.js --apply --database=master
# then --database=tenant (or --tenant=<dbName> one at a time)
node packages/database/dist/migrate-encrypt-pii.cli.js --verify --database=all --set-validation=strict
```

- Progress is stored in `pii_migration_status`; a rerun resumes. `--restart` starts over.
- Every change is a compare-and-swap followed by a re-read; a failed check restores the original.
- Output is counts only.
- `--rollback` restores plaintext, with the original BSON types. Keyed hashes (`TrialClaim.key`) and hashed refresh tokens stay hashed.

### Backup and recovery

- Database backups contain only wrapped keys. They are usable only while the KMS key exists and the restoring role can call `Decrypt`.
- To recover a database you need the backup and the same KMS key (same account and region), or a copy made with KMS multi-region keys.
- Backups taken before the migration contain plaintext until they expire.

## Troubleshooting

| Symptom                                   | Cause                                                                                                                            |
| ----------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| `Field key unavailable for scope`         | KMS unreachable, or the role lacks `Decrypt` for that encryption context.                                                        |
| `FieldCryptoError: AUTH_FAILED`           | A value was moved between records, fields or tenants, or altered. It is not returned.                                            |
| `FieldCryptoError: MISSING_KEY`           | No KMS key configured, or a development process may not create keys on a shared database.                                        |
| `FieldProtectionError: SCAN_LIMIT`        | An in-memory search matched more than the row cap before filtering. Narrow it, or raise the cap.                                 |
| `FieldProtectionError: UNSUPPORTED_QUERY` | The query compares, groups or sorts on an encrypted field in a way that can't be done correctly. Rewrite it in application code. |
| `Document failed validation` (code 121)   | Something wrote plaintext into a protected field without going through the Prisma hook.                                          |
| `SensitiveWriteBlockedError`              | A development process tried to write sensitive data to a shared database. Use the local MongoDB.                                 |
